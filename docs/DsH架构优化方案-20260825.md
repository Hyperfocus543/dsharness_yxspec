# YXSpec 深入优化方案 — 基于 DSH 架构的结构性硬约束

> 目标：把 yxspec 目前的**「prompt 文本软约束」**升级为 **DSH 原生结构性硬约束**。
> 核心原则：**不动 harness 主仓源码 / 不动 yxspec 框架源码**，全部通过网关本地 cordis 插件包实现。
> 日期：2026-08-25 · 状态：**方案待评审 · 阶段 1 POC 已通过**（见 §八）

---

## 一、现状：yxspec 在 DSH 上的实现方式（为什么"浅"）

YXSpec 网关（`.dsh/gateway/`）跑在 DSH harness 之上，但目前是**用 prompt 字符串模拟流程纪律**：

| 能力 | 当前实现 | 问题 |
|---|---|---|
| **门控**（上游未完成禁止启动） | `buildAgentPrompt` 把 `scanGates()` 的 JSON 拼进 prompt「门控扫描结果」 | 模型可忽略；只"建议"不"强制" |
| **工具裁剪**（coding 只许 fs/bash） | prompt 里写「只允许 fs/bash，禁止 web/API 工具」 | 模型可绕过；无结构性拦截 |
| **阶段命令识别** | 网关 `resolveStage()` 用 `prompt.includes('/yxspec:xxx')` 子串匹配 | 脆弱；无 harness 侧注册 |
| **阶段任务计划** | prompt 里要求「先 create_goal 再 todo_write」 | 纯提示，无领域语义 |

**本质**：DSH 有丰富的结构性执行机制（工具 guard 管道 / preset 装配 / commands 注册 / invariants），但 yxspec 只用到了最浅的 `ctx.skills` + prompt 拼接。

---

## 二、DSH 原生的结构性能力（已探查确认）

从 DSH 主仓（`D:/AI/deepseek-harness-master`）能力接缝文档 + 源码确认：

### 1. 工具执行管道（`packages/core/tools`）
```
model 工具调用
  → tools/pre-execute 瀑布（hooks / 权限 / sandbox）
  → monotonic guards（注册的守卫，可 deny）
  → tools/execute 瀑布（超时/重试）
  → tools/post-execute 瀑布（accept/block/replace/add context）
  → tools/result（同步通知）
```
**`ctx.tools.guard(exec => reason|undefined)`**：同步守卫，返回字符串即拒绝执行。`exec.name` / `exec.arguments` / `exec.agent` 可读。

### 2. 命令注册表（`packages/interaction/commands`）
**`ctx.commands.register({ name, description, handler })`**：注册 `/yxspec:*` 命令，`handler` 收到 agent + rawInput，**不把命令发给模型**。

### 3. Agent Presets（`packages/preset/agent-presets`）
**按 agent 挂不同工具面 + prompt section**：每阶段一个 preset，作用域隔离，阶段间不串。全局层隐藏 schema。

### 4. Invariants（`packages/runtime-diagnostics/invariants`）
结构化不变量注册表：跨事件校验状态（如"review 前必须有 signoff"）。

## 三、方案：三阶段落地「深度 1」

### 阶段 1 — 工具 guard（模型不可绕过的工具裁剪）⭐ 最高价值

**目标**：`restrictTools: true` 的阶段（coding/static/verify/auto-test）从 prompt 提示 → 结构性 deny。

**改动**：新建网关本地 cordis 插件包 `@yxspec/tool-guard`（放在 `runtime-js/` 下，经 junction/相对引用挂 cordis.yml，不动主仓）：
- `tools.guard()` 注册守卫，按 `exec.agent` 的 goal 里的阶段 token（如 `swe_coding_do`）判断
- 该阶段 → 非 `fs`/`bash`/`read` 等白名单工具直接返回 deny reason（拒绝执行，模型拿失败反馈）
- 无需改 harness 主仓任何代码

**价值**：工具裁剪从"模型自觉遵守"变"结构性强制"。

### 阶段 2 — 阶段命令注册（取代 includes 子串匹配）

**目标**：25 个 `/yxspec:*` 命令在 harness 侧注册，网关不再靠 prompt 子串匹配。

**改动**：新建 `@yxspec/commands` 插件包：
- `ctx.commands.register()` 注册全部 25 个命令，handler 把命令路由给网关 `/api/agent`
- 网关 `resolveStage()` 改为读 harness 注册表（或保持现状但命令识别更可靠）

**价值**：命令识别从"文本匹配"变"注册表路由"，更可靠、可扩展（slash 命令 / 参数）。

### 阶段 3 — 门控结构性化 + invariants

**目标**：门控从"prompt 注入 JSON"变"结构性检查"。

**改动**：
- guard 里做门控检查：目标阶段上游未完成 → deny 该阶段命令工具调用
- 可选：用 `invariants` 注册"review 前必须有 signoff"等跨事件不变量

**价值**：门控从"建议"变"强制"，且与 DSH 事件流深度集成。

### 踩坑记录（重要，供阶段 2/3 复用）

1. **cordis 依赖注入检查**：插件访问 `ctx.tools` 必须声明 `export const inject = ['tools']`，否则 cordis 报
   `cannot get property "tools" without inject`，**整个插件树加载失败**（表象是 runtime 起不来 / llm 服务未注册 → 误报 `no adapter registered for provider`）。排查约 1 小时，最终靠 runtime stderr 落盘定位。
2. **SDK 驱动报 NO_ADAPTER 的 3 个可能根因**（按优先级排查）：
   - 插件树加载失败（上条，真正根因）
   - 环境缺 key（Git Bash 不继承 `DEEPSEEK_API_KEY`，需手动从 `~/.dsh/.credentials.yaml` 解析注入）
   - settings.yaml 未命中（`~/.dsh/settings.yaml`，`DSH_HOME` 缺省 = `homedir()/.dsh`）
3. **headless runtime 是 JSON-RPC 静默服务**：无 banner 正常；调试插件加载错误靠 **stderr 落盘**，别只盯 stdout。

## 九、阶段 2 实测结论（commands 命令注册）✅ 部分可用 / 落点调整

> 时间：2026-08-25 · 状态：`commands.register` 可用性已验证；runtime 内命令校验因 SDK 通道限制放弃，落点调整为网关侧

### 实测发现（基于 harness 源码 + headless 冒烟）

| 项 | 结果 |
|---|---|
| `ctx.commands.register()` 在 headless runtime | ✅ 可用，27 个 `/yxspec:*` 命令注册成功（含废弃 swe-detail、变体 swe-coding-verify-pc-v2） |
| `commands` 服务注入 | ✅ 需在 cordis.yml 挂载 `@deepseek-ai/dsh-commands`（junction 指向 `packages/interaction/commands`） |
| SDK JSON-RPC 通道命令 wire | ❌ 只支持 `initialize`/`session/prompt`/`shutdown`；`commands/execute` 只走 web UI connection wire |
| 根 ctx 收 `session/event` | ❌ 事件绑定在 session 专属 ctx 作用域，root ctx 的 `ctx.on('session/event')` 收不到 |
| runtime 内命令校验增量 | ❌ 命令以普通文本进 agent，网关 `resolveStage` 已承担命令识别与派活（结构性，非文本子串匹配） |

### 落点调整（务实收敛）

- **放弃**：runtime 内命令合法性校验 + 审计（SDK 通道不可达，事件作用域隔离，与网关职责重复）
- **保留**：`@yxspec/commands` 插件把 25 命令注册进 harness 注册表（名称/描述/阶段映射在 harness 侧可见可查），为未来 web UI wire 接入铺路
- **真正增量**：命令识别与派活由网关 `stages.mjs` 权威表承担（已实现），runtime 侧用 guard 做**门控结构性化**（阶段 3）才是有独立价值的硬约束

### 阶段 3 的定位修正

阶段 3（门控结构性化）被证明是比阶段 2 更有价值的落点：guard 拦截走工具管道、SDK 可达、已验证可行（§八），能把"跳级派活"从 prompt 软约束变结构性硬约束。
