> 原则：架构与机制引用均来自本机实现/官方实搜，不编造。git-RAG 部分按团队目标定位梳理，实现细节待团队确认。

## 一、一句话总览

项目组在做一件事：**把「AI 执行 ASPICE 流程」从一次性交付，变成「越跑越好、越跑越懂团队」的闭环系统**——

> **执行产生数据 → 数据沉淀为知识 → 知识反哺执行与优化**

三个模块各管一层：

| 模块 | 归属 | 层 | 一句话定位 |
|---|---|---|---|
| **DSH 平台** | 林汉飞 | **执行层** | 让 AI **守规矩地跑**流程：结构性硬约束 + 每步留痕 + 无人值守 |
| **自迭代智能体** | 焦凡/蒋玫 | **元层（教练）** | 让 yxspec **自己发现并改进自己**：跑→评→改→护栏，循环至收敛 |
| **git-RAG 团队知识库** | 团队 | **知识层** | 把 git 提交历史变成**可检索的团队知识**，所有后续工作复用 |

```
                    │   结构性约束·门控·审计账本·轨迹·无人值守   │
                    └───────┬──────────────────────▲───────┘
                            │ ① 每轮执行产出审计证据     │ ② 执行效果反馈

                    ┌───────▼──────────────────────┴───────┐
                    │      自迭代智能体（元层·教练）           │
                    │   四能力闭环：自跑→评判→自改→护栏        │
                    │   V1 确定性标准 · 三通道 · 基线回滚       │
                    └─────────────────────────────────────┘
```

**四个咬合点：**

1. **DSH → 自迭代**：DSH 每轮执行产出**审计账本 + 阶段轨迹**（工具调用、token 成本、产物、门控结果）——这就是自迭代「确定性打分」的**数据原料**。没有执行层留痕，自迭代无据可评。
2. **自迭代 → DSH**：打分发现「某节点总出问题」（流程自诊断）→ 按三通道改 yxspec 自身（效率四象限 / 检索 / 本轮报告）→ 改的是**执行层的 prompt/门控/标准** → 再回 DSH 跑——教练改运动员的「训练方法」。
3. **DSH → git-RAG**：DSH 的每次提交（代码/产物/决策记录）就是**知识原子**——git 历史天然记录了「什么阶段、为什么改、改了什么、验证了什么」，无需额外采集。
4. **git-RAG → 自迭代 & DSH**：知识库被检索复用——自迭代的「B 通道开源检索」升级为「**本地团队知识优先检索**」（团队踩过的坑 > 外部通用资料）；DSH 日常执行遇到同类问题直接查团队先例。

## 三、DSH 平台适配原理（重点）

### 3.1 适配目标：把「软约束」变成「硬约束」

yxspec 跑在 DSH harness 之上，最初是**用 prompt 文本模拟流程纪律**——每阶段在给模型的指令里写几句「请遵守」：

| 流程纪律 | 最初的软实现 | 问题 |
|---|---|---|
| 门控（上游未完成禁止启动） | `scanGates()` 结果拼进 prompt「门控扫描结果」 | 模型**可以忽略**——只是建议，不是禁止 |
| 工具裁剪（coding 只许 fs/bash） | prompt 里写「只允许 fs/bash，禁止 web/API」 | 模型**可以绕过**——没有拦截 |
| 阶段命令识别 | `resolveStage()` 用 `prompt.includes('/yxspec:xxx')` 子串匹配 | 脆弱，容易误判 |
| 阶段任务计划 | prompt 里要求「先 create_goal 再 todo_write」 | 纯提示，无领域语义 |

**打个比方**：这就像在墙上贴一张「规章守则」请员工自觉遵守——员工完全可以无视。我们要做的是把规章变成**门禁系统**——不守规矩，**连门都进不去**。

**DSH 恰恰提供了把这些「软约束」变成「硬约束」的原生机制**，但 yxspec 只用到了最浅的 `ctx.skills` + prompt 拼接。适配 = **把流程纪律从 prompt 文本搬进 DSH 原生结构性机制**。

### 3.2 适配原理：DSH 三件套原生机制

#### ① 工具 guard 管道（结构性工具面）

DSH 工具执行是**五段瀑布管道**：

```
模型工具调用
  → tools/pre-execute 瀑布（hooks/权限/sandbox）
  → monotonic guards（注册的守卫，可 deny）
  → tools/execute 瀑布（超时/重试）
  → tools/post-execute 瀑布（accept/block/replace/add context）
  → tools/result（同步通知）
```

- **`ctx.tools.guard(exec => reason|undefined)`**：同步守卫，返回字符串 = **结构性拒绝**该工具执行（`exec.name/arguments/agent` 可读）
- **单调性**：guard deny 后**任何后续瀑布监听器都不能把它翻回允许**——「拒绝了就是拒绝了」
- 拒绝以 `isError:true` 结果反馈模型，模型收到**失败反馈**被迫改用白名单内工具

**适配落点**：给 25 个 ASPICE 阶段各注册一张**专属工具白名单**（如编码阶段只许 fs/read/write/bash，分析阶段才放行 weknora 检索）——白名单外工具被结构性 deny。

#### ② 命令注册表（阶段命令结构化）

**`ctx.commands.register({ name, description, handler })`**：把 `/yxspec:*` 阶段命令注册进 harness，handler 收到 agent + rawInput，**不把命令发给模型**。

**适配落点**：25 个阶段命令注册成 harness 原生命令，取代网关子串匹配。受 SDK JSON-RPC 通道限制（只支持 initialize/session/prompt/shutdown），命令识别落点调整为**网关侧 resolveStage**，但注册表为后续升级留位。

#### ③ 会话事件日志 + 插件装配（审计账本 & 按需能力）

- **会话事件日志**：`session/` 子系统追加式记录每个事件（turn/start、tool/call、assistant/message…）——**单一事实来源**，审计账本的根基
- **Everything-is-a-Plugin**：几乎一切能力 = 可组合插件包，事件驱动，声明式合并扩展——插件可以按需装配/开关

**适配落点**：
- 网关 `harness.mjs` 把 `tool/call + tool/result + turn/end` 追加写 `.dsh/gateway-log/<session>/turn-<n>.jsonl`——**每步工具用了什么、产出什么，可离线审计**
- 阶段执行轨迹插件（`@yxspec/aspice-trajectory`）订阅会话事件，聚合为按阶段落盘的执行轨迹 JSONL——**门控以轨迹为证据**

### 3.3 实现形态：三层插件 + 合成装配

```
┌─────────────────────────────────────────────────┐
│  网关 server.mjs（:8787）— 22 端点               │
│    /api/agent 派活 · /api/events SSE · 门控      │
├─────────────────────────────────────────────────┤
│  lib/ 12 模块                                    │
│    harness.mjs  SDK驱动+串行闸门+超时熔断+合成装配  │
│    stages.mjs   27 阶段映射+门控扫描+agent prompt │
│    trajectory.mjs 轨迹读取+门控三态判定           │
│    gate-enforce.mjs 派活前门控强制                │
│    plugins.mjs   base/plugin/candidate 三层开关   │
├─────────────────────────────────────────────────┤
│  runtime-js/  DSH runtime 装配                   │
│    cordis.yml 主装配                              │
│    cordis.synth.yml 合成装配（插件开关即重建）      │
│    vendor/ 3 个自有插件（junction 只读挂载）       │
│      @yxspec/tool-guard   工具面+门控             │
│      @yxspec/commands     阶段命令注册表           │
│      @yxspec/aspice-trajectory 执行轨迹聚合       │
├─────────────────────────────────────────────────┤
│  DSH harness 主仓（D:/AI/deepseek-harness-master）│
│    只读引用，红线不动                             │
└─────────────────────────────────────────────────┘
```

**装配机制（开关即重建）**：`plugins.mjs` 把插件分为 base（基座必需，不可关）/ plugin（已装配，可关）/ candidate（POC 已验证，可开）三层；改动开关 → 写合成装配 `cordis.synth.yml` → 重建 runtime 子进程。**所有能力都是插件、都能开关**（DSH 设计哲学）。

**工程纪律**：
- **红线**：不动 harness 主仓源码 / 不动 yxspec 框架源码 / 不读 _monitor——插件全部经网关本地 vendor 包
- **挂载方式**：junction（`fs.symlinkSync`）只读引用，不动主仓
- **副本验证纪律**：改动先副本端口（8789）冒烟 → 独立验证 → 确认 → 切主（8787），主网关日间不中断
- **异地备份**：每步 `git commit` + push GitHub

| 能力 | 实证结果 |

| 门控结构性化 | 跳级派活（上游未完成调 `sqt-strategy`）→ 结构性拒绝，返回 `blocked`，不只是提示 |

| 单测 | 62/62 全通过（全阶段白名单放行 + web_search 全阶段 deny + write 回归 + 门控）|

### 3.5 三期递进（适配深度演进）

| 期 | 内容 | 状态 |
|---|---|---|
| **一期**（8-25）| 工具 guard POC + 门控结构性化——「工具裁剪 + 门控」从 prompt 搬进结构 | ✅ 实证 |
| **二期**（8-26）| 插件化四方向：A guard 全阶段白名单+门控（✅）｜ B 阶段=agent preset ｜ C invariants ｜ D subagent | A 完成，B/C/D 探路 |

**混合注入策略**：小而关键的阶段知识（brief/模板/门控/追溯要求）继续 prompt 注入（不能省）；大而按需的规则（PRD 六维评分/审查检查单/coding-specs 编码规范 2-4KB）进 `.dsh/skills/` 走 `skill()` 按需调起（省上下文、聚焦）。

### 3.6 能力矩阵（我们做了什么 vs DSH 原生）

| 我们的能力 | 对应 DSH 原生机制 | 价值 |
|---|---|---|
| per-阶段工具面 | 工具管线 + 单调 guard + 作用域 | 结构性拒绝，模型无法绕过 |
| 上游门控链 | guard 内读 `dsh_state.current` 做上游检查 | 跳级被禁行整个阶段 |
| 审计账本 | 会话事件日志（单一事实来源）| ASPICE 每步有据可查 |
| 轨迹体系 | session-query trace 能力的 ASPICE 化 | 追溯断链可定位，门控有证据 |
| 插件统一开关层 | Everything-is-a-Plugin | 能力按需装配、开关即重建 |
| 无人值守 | 断点续跑 + 超时自愈 + 静默拒绝 | 过夜批量跑 25 阶段不需要人盯 |
| 内网私有化 | 内网大模型 + 数据不出内网 | 合规安全 |

## 四、自迭代智能体（焦凡/蒋玫）——元层：让 yxspec 自己改进自己

**要解决的问题**：人工驱动迭代效率低——人看一遍报告再决定改哪，慢且容易漏。

**机制**：
- **元层定位**：「教练不住赛道」——独立于执行层之外，物理隔离防误伤，跨项目可移植
- **四能力闭环**：自跑 → 评判（V1 确定性标准：MasterScore 6 维 21 项 + StageScore）→ 自改（三通道：A 效率四象限 / B 开源检索 / C 本轮报告）→ 护栏（改前冻结快照 → 改后逐项对比 → 降级即回滚）
- **核心纪律**：评判必须**确定性可验证，禁止 LLM 自评**——锚定效应实验（两轮 16 次审查，6/6 与 10/10 全抓到缺陷）证明「判定项可验证性」才是抗自欺机制；LLM 自评会自我偏好、永远「看起来通过」，循环变成自欺
- **知识自沉淀**：每次迭代的坑自动固化为规则——这是人驱动迭代给不了的差异化价值

## 五、git-RAG 团队知识库（团队）——知识层：让团队知识可复用

**目标**：从 git 提交历史构建 RAG 知识库，后续所有工作都能复用团队知识。

**与 DSH 的关系**：DSH 的提交历史就是知识库的**原料库**——每个 commit（阶段产物、决策记录、踩坑修复、验证结果）都是结构化的知识原子，天然带「为什么/改了什么/验证了什么」的上下文。

**与自迭代的关系**：自迭代的「知识自沉淀」产物（坑 → 规则）是**高质量的 RAG 知识源**——比原始 commit 更凝练（已经过打分筛选和优化验证）；反之，RAG 检索可以成为自迭代「B 通道」的本地增强。

## 六、团队闭环（汇报核心落点）

**没有形成闭环之前**：
- DSH 能跑流程，但跑完的「经验」躺在 git 历史里没人用
- 自迭代能优化节点，但优化依据来自人工观察 + 外部资料，缺团队自己的历史证据
- 知识库没有持续的原料供给，建成即过期

**形成闭环之后**：
```
每次执行（DSH）→ 留下可审计记录（git 提交 + 审计账本）
→ 沉淀为可检索知识（git-RAG）
→ 支撑下一次执行（DSH 查先例）与下一轮优化（自迭代查团队坑）
→ 自迭代的坑固化规则再回流知识库（知识越滚越厚）
```
**一句话**：DSH 提供「跑得规矩」的执行底座，git-RAG 提供「跑得有积累」的知识底座，自迭代智能体让三者**自动循环、越跑越好**——这是「AI 驱动 ASPICE 流程」从一次性工具走向**组织级智能体**的关键差异。
